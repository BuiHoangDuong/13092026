Hai luồng chạy song song. Ban đầu nhập báo cáo thủ công; lịch 15–30 phút chỉ bật khi có nguồn tự động. Client đọc dữ liệu qua server.

Client và server: client gửi yêu cầu; server kiểm tra quyền, đọc database và trả kết quả. Giao diện đang mở có thể đọc lại mỗi 30 giây.

Worker và server: mũi tên vào server biểu diễn module ingestion của backend. Module dùng chung này có thể được worker gọi trực tiếp để ghi database; không bắt buộc thêm một HTTP API nội bộ.

Mũi tên ở cây này: package cung cấp định nghĩa cho ứng dụng sử dụng. Đây là quan hệ dùng chung code, không phải request hoặc dữ liệu chạy qua mạng. Client không import core hoặc db.

“Crawl” ở đây là khối lấy dữ liệu dự kiến: phương thức cụ thể có thể là API, file xuất từ tài khoản root affiliate hoặc tự động đọc web nếu nguồn cho phép và thực hiện được. Chưa có crawler hoặc kết nối sàn đang chạy. Dữ liệu chi tiết đến đâu phụ thuộc nguồn.

T1 / TECHNICAL ARCHITECTURE

Triển khai frontend và backend như thế nào?

Đề xuất hiện tại: cùng một repo, client/server/worker chạy độc lập và một PostgreSQL dùng chung. Công nghệ chưa được chủ dự án chốt và chưa cài đặt.

Luồng tương lai: lịch 15/30 phút → tạo job API → worker gọi sàn → cùng bước chuẩn hóa và lưu. Luồng này tắt cho đến khi xác nhận có API phù hợp.

Kết nối chung: worker → PostgreSQL; API → PostgreSQL → frontend. Báo cáo được lấy thủ công, phần xử lý và cập nhật website được tự động hóa.

Backend gồm hai phần: API phản hồi thao tác của người dùng và worker xử lý tác vụ nền. Chúng có thể chạy trên cùng máy chủ lúc đầu, nhưng có vòng đời độc lập.
Hướng đi đã xác nhậnTheo dõi tài khoản từ dữ liệu root affiliate; nhập thủ công trước

Upload báo cáo → kiểm tra → xác nhận → hiển thị theo UID

  1. Chọn nguồn: sàn, tài khoản root, loại báo cáo, khoảng thời gian và múi giờ của báo cáo. CSV/XLSX là định dạng dự kiến; chưa có file mẫu để xác nhận cột.
  2. Upload riêng tư: API kiểm tra quyền quản trị, loại và kích thước file; lưu file gốc vào object storage riêng tư, tạo import_batch và job rồi trả 202 Accepted. Không giữ HTTP request mở để parse cả file.
  3. Worker kiểm tra: đọc UID như chuỗi, chuẩn hóa timestamp/decimal, phát hiện dòng lỗi, UID chưa ánh xạ, bản ghi trùng và tổng số liệu. Không thực thi công thức hoặc macro trong bảng tính.
  4. Xem trước: quản trị viên xem số dòng mới, trùng, bị lỗi, dữ liệu xung đột và tổng kiểm tra. Batch chưa được công bố cho dashboard dữ liệu chính.
  5. Xác nhận nhập: API tạo job công bố; worker upsert/ghi phiên bản có nguồn gốc và commit nguyên batch. Lỗi ở giữa không để dashboard đọc một nửa dữ liệu.
  6. Đọc theo tài khoản: quản trị viên lọc theo sàn + UID; nếu mở cho khách tự xem sau này, API lấy danh sách UID đã xác minh từ phiên đăng nhập, không tin UID tự gửi từ trình duyệt.

Mức chi tiết do báo cáo quyết định. File có trade ID và từng giao dịch thì có thể thiết kế lịch sử giao dịch; file chỉ có volume/hoa hồng theo ngày thì lưu và hiển thị số liệu tổng hợp. Không suy ra các giao dịch không xuất hiện trong nguồn.

1. Frontend — Next.js, React, TypeScript

  • Trang công khai render HTML phía máy chủ để có nội dung ngay; các phần lọc, chọn sàn và dashboard chạy tương tác trong trình duyệt.
  • Dùng TanStack Query cho dữ liệu động: trạng thái tải, lỗi, tải lại và polling API nội bộ.
  • Dashboard đọc lại API server mỗi 30 giây khi tab đang hiển thị; dừng polling khi tab ẩn, tải lại khi quay về.
  • Hiển thị thời điểm đồng bộ thành công và trạng thái nguồn dữ liệu. Dữ liệu chưa có không hiển thị thành số 0.

Frontend chỉ hiển thị dữ liệu backend cho phép; không tự tính khoản cashback phải trả.

2. Backend API — ứng dụng Node.js riêng

  • Nhận request tại /api/* và /go/:linkId; xác thực, phân quyền và kiểm tra đầu vào ở phía máy chủ.
  • HTTP handler chỉ điều phối; logic nằm trong services dùng chung giữa server và worker. Client, kể cả phần render HTML của Next.js, lấy dữ liệu qua API với đúng ngữ cảnh xác thực.
  • Đọc PostgreSQL để trả JSON nhanh; không gọi API sàn mỗi khi khách tải trang.
  • API dashboard riêng tư trả Cache-Control: private, no-store. Bản đầu không cache dữ liệu tài chính động.

Đề xuất v0.3 tách API khỏi Next.js để phân chia client/server rõ ràng trong cùng repo. Framework backend cụ thể chưa chốt; frontend không import core hoặc db.

3. Worker — tiến trình Node.js riêng

  • Bản đầu dùng adapter đọc báo cáo cho từng sàn. Worker chạy thường trực và kiểm tra job chờ trong PostgreSQL mỗi 10 giây.
  • Job parse tạo dữ liệu staging để xem trước; job publish chỉ chạy sau khi quản trị viên xác nhận. Các job dài tách khỏi request web.
  • Claim job bằng transaction với FOR UPDATE SKIP LOCKED, lease và heartbeat. Worker chết thì job có thể nhận lại; kiểm tra quyền sở hữu lease trước commit để ngăn worker cũ ghi đè.
  • API và worker dùng chung schema/services. API adapter tương lai đi vào cùng đường chuẩn hóa, chống trùng và công bố dữ liệu.

Đề xuất dùng hàng đợi PostgreSQL cho quy mô khởi đầu; chưa cần Redis. Nếu backlog hoặc throughput tăng đáng kể thì đánh giá BullMQ/Redis hoặc một hệ job chuyên dụng.

4. PostgreSQL — nguồn dữ liệu của ứng dụng

  • Đề xuất Prisma cho schema/migrations. Các nhóm mới: job, import batch, staging rows, tài khoản theo sàn/root/UID và báo cáo đã công bố.
  • Dữ liệu từng giao dịch chỉ tạo khi file đủ chi tiết; nếu không thì dùng snapshot theo kỳ. Giữ liên kết đến batch/file gốc để kiểm tra nguồn.
  • Giá trị tiền dùng decimal/numeric; API trả chuỗi thập phân kèm loại tài sản. UID dùng chuỗi, thời gian chuẩn hóa UTC và giữ thông tin múi giờ nguồn.
  • Không cộng snapshot tổng nhiều lần. Các kỳ báo cáo chồng lấn phải được giải quyết trước khi tính tổng; không tự cộng tất cả báo cáo đã tải lên.

Theo dõi volume/hoa hồng không đồng nghĩa đã xây số dư hoặc chức năng chi trả cashback. Các phần này chưa nằm trong bản đề xuất triển khai đầu tiên.

5. Triển khai — web, worker và lưu trữ riêng tư

  • Đề xuất một VPS Linux chạy reverse proxy HTTPS, container client, server và worker thường trực; PostgreSQL quản lý riêng và object storage riêng tư cho file nhập.
  • Upload tạo job ngay, worker nhận trong lần kiểm tra kế tiếp; không phải chờ mốc 15 phút.
  • Khi có API: systemd timer thêm job đồng bộ vào PostgreSQL mỗi 15/30 phút. Job dùng khóa theo nguồn để tránh chạy chồng; lịch API tắt ở bản nhập file.
  • Deploy image cố định; migration chạy một lần. Theo dõi web health, tuổi job lâu nhất, heartbeat worker và tỷ lệ import lỗi; kiểm tra backup/restore dữ liệu.

Local có thể dùng Docker Compose. Chưa tạo container, queue, timer hoặc kết nối storage trong repo.

6. Nguồn dữ liệu — báo cáo root affiliate trước

  • Hướng đi người dùng xác nhận: muốn theo dõi giao dịch của tài khoản từ dữ liệu root affiliate, có thể phải lấy thủ công trước.
  • Chưa có file mẫu để biết CSV/XLSX, cột UID, trade ID, khoảng thời gian, múi giờ hoặc mức chi tiết có sẵn.
  • Adapter phải phân biệt từng giao dịch với báo cáo tổng hợp. Nếu chưa đủ khóa nhận diện ổn định, không bật tự động gộp dòng vì có thể mất hoặc trùng giao dịch.
  • API là nâng cấp sau khi xác nhận quyền và đúng loại dữ liệu; không mặc định WebSocket giá thị trường cung cấp dữ liệu affiliate.

Ví dụ giới hạn nguồn: tài liệu Bybit ghi một số trường volume affiliate cập nhật T+1. Nguồn: Bybit API.

Cấu hình & ranh giới truy cập

  • Đề xuất biến DATABASE_URL, APP_URL, API_INTERNAL_URL, WORKER_POLL_SECONDS, SYNC_INTERVAL_MINUTES, IMPORT_STORAGE_BUCKET và JOB_TIMEOUT_SECONDS.
  • Quyền truy cập kho file chỉ cấp cho API/worker. Credential theo sàn trong giai đoạn API chỉ tồn tại ở worker/secret store; tên cụ thể theo SDK hoặc adapter được chọn. Không dùng tiền tố biến công khai cho secret.
  • API quản trị cần xác thực. API của khách hàng chỉ bổ sung sau khi có cơ chế liên kết và xác minh chủ sở hữu UID.
  • PostgreSQL chỉ nhận kết nối từ dịch vụ backend/worker; đặt web, worker và database gần nhau về vùng triển khai.

Không biến nào ở đây đã được tạo trong repo. Chưa chọn nhà cung cấp VPS, database hoặc giải pháp đăng nhập.

Cơ sở kỹ thuật cho frontend: Next.js: tự triển khai. Lựa chọn stack và cách chia tiến trình ở đây là đề xuất cho dự án, không phải yêu cầu bắt buộc của các framework.

T2 / DATA FRESHNESS

Realtime hay batch 15–30 phút?

Bản đầu: cập nhật sau khi nhập báo cáo. Khi có nguồn API: bật lịch 15/30 phút. Giao diện có thể đọc backend mỗi 30 giây trong cả hai trường hợp.

Nhập tay ở nguồn, tự động ở hệ thống

Giả sử bạn tải báo cáo lúc 14:00 nhưng báo cáo chỉ có dữ liệu đến 12:00, website phải ghi “dữ liệu đến 12:00”. Polling 30 giây hay SSE không bổ sung giao dịch sau 12:00. Sau khi upload, worker xử lý và đợi xác nhận công bố; không cần giữ file lại đến mốc batch 15 phút.

Chu kỳ 15 phút: ví dụ này mất tối đa 10 phút 30 giây từ lúc sàn công bố đến lúc giao diện thấy dữ liệu.

Luồng batch API — chỉ bật ở giai đoạn sau

  1. Scheduler tạo job trong PostgreSQL mỗi 15 phút, có thể đổi thành 30. Worker đang chạy nhận job.
  2. Lấy khóa theo nguồn và đọc checkpoint của lần đồng bộ thành công trước.
  3. Gọi API đúng quyền, đi qua đủ trang dữ liệu, giới hạn tốc độ theo tài liệu từng endpoint.
  4. Chuẩn hóa và kiểm tra; dùng khóa nguồn để chống trùng với cả dữ liệu API lẫn file đã nhập. Nếu chưa có khóa đối chiếu đáng tin cậy, giữ tách nguồn và đối soát trước khi hợp nhất.
  5. Commit bản dữ liệu hoàn chỉnh và checkpoint cùng bước công bố. Nếu lỗi, giữ bản thành công trước và không tăng checkpoint.
  6. Frontend đọc bản mới qua API trong lần polling tiếp theo.

Độ bền khi API sàn lỗi hoặc dữ liệu đổi

  • Retry lỗi tạm thời với backoff và jitter; HTTP 429 tuân thủ thời gian chờ của nguồn. Lỗi xác thực phải báo cấu hình, không retry vô hạn.
  • Chạy lại cùng batch không tạo thêm hoa hồng. Bản ghi dùng khóa nguồn; snapshot dùng khóa sàn/root/UID/kỳ/tài sản.
  • Đồng bộ lại một khoảng dữ liệu gần đây để nhận cập nhật muộn. Độ rộng khoảng này chốt riêng cho từng endpoint sau khi xem dữ liệu thật.
  • Lưu last_success_at và source_as_of nếu nguồn cung cấp. Một lần gọi API thành công không có nghĩa nguồn đã có dữ liệu mới.
  • Cảnh báo khi hai chu kỳ liên tiếp không thành công hoặc vượt thời gian job cho phép. Dữ liệu cũ vẫn hiện với nhãn trễ; chưa có bản thành công thì hiện “chưa có dữ liệu”.

Khi cần realtime: thêm SSE giữa backend và frontend

SSE là kết nối HTTP một chiều để server báo cho trình duyệt khi có thay đổi. Sau khi worker commit dữ liệu, PostgreSQL có thể phát tín hiệu NOTIFY; API giữ kết nối lắng nghe riêng rồi gửi sự kiện “dataset changed”. Frontend nhận tín hiệu và tải lại dữ liệu đã được phân quyền.

Worker commit → PostgreSQL NOTIFY → Backend SSE → Frontend refetch API
                                                        ↓
                                              Hiển thị bản đã lưu

Đây là phương án nâng cấp, chưa cần cho bản đầu. PostgreSQL NOTIFY chỉ dùng để báo thay đổi, không phải hàng đợi bền vững; khi reconnect frontend phải tải snapshot hiện tại để bù sự kiện bỏ lỡ. Kết nối SSE cần xác thực, heartbeat và reverse proxy hỗ trợ streaming. WebSocket chỉ cần khi có giao tiếp hai chiều liên tục.

Tham khảo: MDN: Server-sent events, PostgreSQL: NOTIFY. Chưa giả định các sàn cung cấp webhook cho dữ liệu affiliate.

Tiêu chí kiểm tra khi triển khai pipeline thật

  • Import báo cáo mẫu: UID giữ nguyên, timestamp đúng múi giờ, decimal không sai số; xác định đúng loại giao dịch hay số liệu tổng.
  • Upload lại cùng file hoặc báo cáo chồng kỳ không làm tăng tổng; dòng lỗi hoặc khóa dữ liệu không rõ phải được báo trước khi công bố.
  • Preview không đổi dashboard; commit lặp hoặc worker chết giữa chừng không tạo batch dở dang. Worker nhận lại job không được ghi trùng.
  • Người không có quyền không xem được raw file, trạng thái import hoặc dữ liệu tài khoản; UID chưa liên kết không tự gán cho khách.
  • Job chạy khi không có khách truy cập; thử cả lịch 15 phút và 30 phút.
  • Gọi lặp cùng batch, chạy hai worker đồng thời và crash giữa batch: không trùng dữ liệu, không công bố kết quả dở dang.
  • API phân trang, trả HTTP 429/5xx, hết quyền hoặc trả cập nhật muộn: checkpoint và trạng thái phản ánh đúng.
  • Dashboard không gọi trực tiếp API sàn, không đọc chéo dữ liệu riêng tư và không cộng snapshot nhiều lần.
  • Phân biệt không có dữ liệu với giá trị 0; hiển thị đúng lần đồng bộ và thời điểm dữ liệu nguồn.
  • Nếu bật SSE, kiểm tra reconnect, bỏ lỡ sự kiện, xác thực và buffering ở reverse proxy.

Các tiêu chí trên chưa được chạy vì ứng dụng chưa tồn tại. Kiểm tra tài liệu HTML được ghi riêng trong nhật ký.

04 / DATA FLOW

Hai luồng hoạt động chính

Mô tả hành vi dự kiến, không phải tính năng hiện đang chạy.

Khách tìm ưu đãi → mở link

  1. Xem thông tin đã công bố

    Website lấy thông tin sàn, ưu đãi và hướng dẫn qua lớp xử lý dữ liệu.

  2. Chọn ưu đãi tại trang chi tiết

    Khách đọc điều kiện rồi bấm nút mở link giới thiệu.

  3. Máy chủ tìm link và ghi nhận lượt bấm

    Điểm chuyển hướng lấy link đã cấu hình và tạo sự kiện gắn với link đó.

  4. Trình duyệt chuyển đến sàn

    Việc đăng ký và giao dịch diễn ra trên sàn. Website chưa nhận xác nhận chuyển đổi.

Quản trị cập nhật → website hiển thị

  1. Đăng nhập vào khu vực quản trị

    Máy chủ kiểm tra quyền cho các thao tác quản trị.

  2. Chỉnh sửa nội dung hoặc link

    Quản trị viên cập nhật sàn, ưu đãi, điều kiện, link và bài hướng dẫn.

  3. Kiểm tra và lưu dữ liệu

    Lớp xử lý dữ liệu kiểm tra đầu vào, quyền thao tác rồi lưu vào cơ sở dữ liệu.

  4. Website hiển thị dữ liệu đã công bố

    Lần đọc tiếp theo trả dữ liệu mới; nếu có cache, cơ chế cập nhật phải được xác định lúc triển khai.

Trước khi triển khai cần chốt hành vi với link hết hiệu lực, lỗi ghi lượt bấm, lọc bot và thời gian lưu dữ liệu. Không tự bổ sung giả định rằng lượt mở link tạo ra khoản hoàn phí.

Quy trình cho phiên sau

  1. Đọc toàn bộ file, đặc biệt context repo, sổ quyết định, chi tiết khối và nhật ký.
  2. Kiểm tra hướng dẫn repo, trạng thái Git và các file thực tế; phát hiện chênh lệch với tài liệu.
  3. Phân biệt yêu cầu đã chốt, đề xuất và câu hỏi còn mở. Không coi sơ đồ là tính năng đã tồn tại.
  4. Triển khai theo yêu cầu mới; cập nhật sơ đồ, route, nhóm dữ liệu và quyết định nếu có thay đổi.
  5. Ghi lại công nghệ thực tế, lệnh chạy/kiểm tra, tên biến môi trường và kết quả kiểm tra; không ghi giá trị bí mật.
  6. Cập nhật ngày, nhật ký và việc còn lại trong cùng thay đổi với mã nguồn.

Việc còn lại trước khi xây sản phẩm

  1. Rà soát kiến trúc và phạm vi phiên bản đầu với chủ dự án.
  2. Xác nhận mô hình cashback, đối tác, thị trường và ngôn ngữ; xác định có cần các khối mở rộng không.
  3. Đối chiếu file báo cáo mẫu để chốt độ chi tiết, cột, khóa dữ liệu và parser; xác nhận stack đề xuất, xác thực và môi trường triển khai.
  4. Thiết kế giao diện, hợp đồng dữ liệu, xử lý lỗi link và tiêu chí kiểm tra.
  5. Tạo mã nguồn ứng dụng, tích hợp dữ liệu thực, kiểm tra và triển khai khi được yêu cầu.

Giới hạn: file không tự đồng bộ với repo và không thay thế toàn bộ mã nguồn. Nếu phát hiện khác biệt, kiểm chứng trước rồi cập nhật lại tài liệu.

Cách kiểm tra tài liệu này

  • Mở trực tiếp bằng trình duyệt; bấm các khối và kiểm tra phần nhiệm vụ, đầu vào, đầu ra, quan hệ.
  • Kiểm tra liên kết điều hướng và liên kết đến mô tả đầy đủ; thử điều khiển bằng bàn phím.
  • Xem ở màn hình máy tính và điện thoại: chữ không chồng lên nhau, sơ đồ chuyển thành các luồng dọc.
  • Tắt JavaScript rồi tải lại: sơ đồ và toàn bộ nội dung vẫn hiện; liên kết khối dẫn đến mô tả.
  • Mở chế độ in: điều hướng và bảng tương tác được ẩn, nội dung chi tiết được mở đầy đủ.
